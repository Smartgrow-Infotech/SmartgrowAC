METHOD — WHAT WORKED / WHAT DIDN'T
--------------------------------------------------------------------------------
WORKED:
1. Homepage + all 60 sitemap pages fetched as raw HTML (server-rendered
   WordPress/Bricks). Full <head> intact — nothing stripped.
2. Exactly ONE first-party stylesheet exists and it was fetched in full:
   /wp-content/uploads/tanous-static/design-system.css — 96,980 bytes,
   1,108 lines, hand-authored, unminified, with comments. This makes almost
   every value in this document [VERIFIED] rather than estimated.
3. The single first-party script was fetched in full:
   /wp-content/uploads/tanous-static/app.js — 2,719 bytes, 74 lines.
4. Google Fonts stylesheet URL read from <head> (families + weights + display).
5. Section structure, class names and DOM order extracted from raw HTML.
6. Brand/press/media-kit page: searched /brand, /brand-kit, /press, /media-kit,
   /style-guide and every footer link. NONE EXISTS — so the CSS token block is
   the authoritative source and is treated as such.

DIDN'T APPLY / NOT NEEDED:
· No hashed bundles, no CSS-in-JS, no build-tool obfuscation — nothing was
  undiscoverable.
· No client-side rendering, so no "shell only" problem.
· Rendered screenshots were not available in this environment, so anything that
  depends on seeing pixels (exact contrast ratios as rendered, real image
  crops, actual marquee visual density) is marked [EST] or listed in §16.

0. BUILD & STACK
================================================================================

FRAMEWORK
  WordPress. [VERIFIED — /wp-content/ paths, /wp-admin/ in robots.txt,
  wp comment/RSS feed links in <head>]
  Page builder: BRICKS BUILDER. [VERIFIED — the CSS contains a section commented
  "/* Bricks conversion compatibility */" targeting .brxe-section,
  .brxe-container, .brxe-block, .brxe-html, .brxe-heading, .brxe-text-basic,
  .brxe-shortcode; the legal pages contain a skip link to #brx-content]
  SEO plugin: Yoast SEO. [VERIFIED — "<!-- / Yoast SEO plugin. -->" comment on
  /privacy-policy/ and /terms/]
  Forms plugin: Gravity Forms. [VERIFIED — gform_* JS bootstrap in <head>,
  .gform_wrapper / .gfield / .gform_button classes styled in the CSS]

RENDERING
  100% server-side rendered. Every section — nav, mega-menus, mobile drawer,
  FAQ accordions, pricing tab panels, carousels, forms — is present in the
  initial HTML. [VERIFIED — full-text search of all 60 raw HTML files]
  NOTHING hydrates client-side. There is no framework runtime at all.
  JS is used only for three progressive-enhancement behaviours (see §8).

CSS APPROACH
  Vanilla hand-written CSS in a single flat file, using CSS custom properties
  for tokens. [VERIFIED]
  · NO Tailwind, NO CSS modules, NO styled-components, NO SCSS artifacts.
  · NO reset library — a 6-line hand-rolled reset at the top.
  · Naming convention is BEM-ish: `.block__element` and `.block--modifier`
    (e.g. `.hero-e__image-card`, `.rvr__col--featured`, `.btn--primary`).
  · State classes use an `is-` prefix (`.is-open`, `.is-active`, `.is-show`)
    plus one legacy `.open` and `.scrolled`.
  · Uses modern CSS: `:has()` selectors (4 instances), `aspect-ratio`,
    `backdrop-filter`, `scroll-snap-type`, `clamp()` throughout,
    `border-block`, CSS `mask-image`, native `<dialog>` with `::backdrop`.
  · One second inline <style> block per page: a 1-rule honeypot-hiding snippet
    with id="tanous-gf-honeypot-css". [VERIFIED]

ANIMATION / SCROLL / 3D / SLIDER / TRANSITION LIBRARIES
  NONE. Zero third-party animation, scroll, 3D or slider libraries.
  [VERIFIED — the only <script src> tags on any page are Google gtag and the
  site's own app.js]
  · No GSAP / ScrollTrigger · No Framer Motion / Motion One / Anime.js
  · No Lenis / Locomotive / Smooth Scrollbar (smooth scroll is native
    `html { scroll-behavior: smooth; }`)
  · No Three.js / Spline / R3F · No Lottie / Rive
  · No Swiper / Splide / Embla (carousels are native CSS scroll-snap)
  · No Barba / View Transitions API · No jQuery loaded by the theme (Gravity
    Forms may pull its own; the site's own code feature-detects `window.jQuery`)
  · No custom cursor script · No preloader

FONT HOST
  Google Fonts, with preconnect. [VERIFIED]
    <link rel="preconnect" href="https://fonts.googleapis.com">
    <link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
    https://fonts.googleapis.com/css2?family=Fraunces:opsz,wght@9..144,400;
      9..144,500;9..144,600;9..144,700&family=Inter:wght@400;500;600;700
      &display=swap
  No @font-face declarations of their own. No next/font, no size-adjust metas.
  font-display: swap (via the Google `&display=swap` parameter). [VERIFIED]

IMAGE PIPELINE
  Mixed and unoptimised-looking. [OBSERVED from src attributes]
  · Formats in use simultaneously: .webp, .png, .jpg, .svg — no single pipeline.
    Brand logos alone span all four (Fujitsu-Logo.svg, brand-carrier.webp,
    bryant-logo-rgb.jpg, aos_logo_cmyk.png).
  · Hero and section photography is delivered as CSS `background-image` on
    pseudo-elements, NOT as <img> — so those images cannot be lazy-loaded,
    srcset'd or served responsively. [VERIFIED — ~30 `.hero-e--photo-*` rules]
  · One WordPress-generated size suffix seen ("Updated-image-1024x131.png"),
    indicating WP media sizes exist but srcset is not consistently used.
  · No AVIF. No quality/optimizer query strings. No CDN image service.
  · og:image is 1200×630. [VERIFIED]

PRELOADER
  None. [VERIFIED]

ANALYTICS / CHAT / BOOKING WIDGETS
  · Google Analytics 4 — gtag.js, measurement ID G-3LMBDX9YM4, loaded `async`.
  · A hand-written GA4 event layer (inline <script id="tanous-ga4-events">)
    firing: phone_call_click, email_click, financing_click, popup_form_open,
    mobile_menu_open, service_cta_click, generate_lead.
  · Gravity Forms (form rendering + submission).
  · Google Maps iframe embeds on city pages.
  · NO chat widget. NO booking/scheduling widget. NO heatmap/session-recording
    tool. NO consent-management platform. NO Facebook/LinkedIn/TikTok pixel.
  [ALL VERIFIED]

--- JAVASCRIPT-DRIVEN BEHAVIOUR (all of app.js, 3 IIFEs) ---
  1. HEADER SCROLL SHADOW
     `h.classList.toggle('scrolled', window.scrollY > 8)` on a passive scroll
     listener, run once on load. `.site-header.scrolled` adds `--shadow-sm`,
     transitioned over 220ms. That is the entire scroll effect on the site.
  2. MOBILE DRAWER + ACCORDION
     open() adds `.is-open` to drawer and backdrop, sets
     `aria-expanded="true"` on the hamburger, and sets
     `document.body.style.overflow = 'hidden'` (scroll lock).
     close() reverses all of it. Bound to: hamburger click, close-button click,
     backdrop click, Escape keydown, and ANY link click inside the drawer.
     Accordion: clicking `.mobile-nav-item__trigger` toggles `.is-open` on the
     parent and syncs `aria-expanded`.
  3. STICKY MOBILE CTA BAR
     Shows when `window.scrollY > heroHeight * 0.6` AND the footer's
     `getBoundingClientRect().top >= window.innerHeight - 80`.
     Toggles `.is-show` (transform translateY(100%) → 0, 280ms).
     Guarded with a `last` flag so the class is only written on change.
     Listens to scroll and resize, both passive.

  NOT IN app.js (and therefore presumed inline elsewhere or non-functional):
     · the FAQ accordion open/close (`.faq-row.open`)
     · the pricing plan tab switching (`.plan-option.is-active` /
       `.plan-detail.is-active`)
     · the carousel prev/next arrows
     · the modal open/close (`[data-tanous-open-modal]` is referenced by the GA4
       tracker but no handler exists in app.js)
     See §16.

--- REDUCED-MOTION HANDLING ---
  NONE. There is no `@media (prefers-reduced-motion: reduce)` block anywhere in
  the 1,108-line stylesheet. [VERIFIED]
  The 60s marquee and the 2.4s infinite pulse both run regardless of user
  preference. This is the clearest accessibility defect in the design system.

--- OVERALL MOTION "FEEL" ---
  Restrained and utilitarian. One easing curve and one duration for essentially
  everything:
    --ease: cubic-bezier(.4,0,.2,1)   (Material "standard" easing)
    --duration: 220ms
  Exceptions: 280ms (mobile CTA bar), 380ms (drawer + backdrop), 60s (marquee),
  2.4s (pulse), and `visibility 0s linear <duration>` delay tricks on the
  mega-menu and drawer backdrop.
  The character is: instant feedback, small distances (1–4px), no easing
  personality, no entrance animation. Motion is used to confirm interaction,
  never to decorate.

--- FOCUS-VISIBLE STYLES ---
  NONE for buttons, links, nav items, accordions, tabs, carousels or the
  hamburger. There is no `:focus`, `:focus-visible` or `outline` rule anywhere
  in the stylesheet except the two that REMOVE it (`outline: none` on form

  Partial credit: `.megamenu` opens on `:focus-within`, so keyboard users CAN

--- PREFERS-REDUCED-MOTION ---
  NO support. The 60s infinite marquee and the 2.4s infinite footer pulse run

--- OTHER A11Y OBSERVATIONS ---
  GOOD:
    · 44px minimum touch targets throughout
    · `aria-expanded` is correctly set and synced on the hamburger and on every
      mobile accordion trigger (in app.js)
    · Escape closes the drawer
    · The mega-menu responds to `:focus-within`
    · `<dialog>` is used natively for the modal (free focus trap + Escape)
    · Real semantic landmarks: `<header>`, `<section>`, `<footer>`, `<nav>`
    · Descriptive `alt` text on hero and brand images
    · `img, svg { display: block; max-width: 100%; height: auto; }` prevents
      layout overflow
  PROBLEMS:
    · No skip link on the 58 designed pages (only on the two Bricks legal pages)
    · No visible focus indicator (above)
    · No `prefers-reduced-motion` (above)
    · `ul { list-style: none }` is applied globally without a compensating
      `role="list"`, which suppresses list semantics in Safari/VoiceOver
    · No active/current-page indication in the nav
    · `.gform_validation_errors` (the summary error region) is
      `display: none` — screen-reader users lose the aggregated error message
    · Error state is communicated by colour alone (red text, no icon, no border
      change)
    · The `.hero-e__reviews::after` strapline is CSS `content` — generated
      content is inconsistently exposed to assistive tech
    · Gravity Forms inputs at 14px trigger iOS zoom-on-focus
    · `.faq-row__a` toggles via `display`, so there is no `aria-hidden` /
      `aria-controls` relationship visible in the CSS layer

--- PERFORMANCE ---
  STRENGTHS:
    · ONE 97KB stylesheet and ONE 2.7KB script — a remarkably small critical
      path for a 60-page site
    · Zero third-party JS frameworks or animation libraries
    · Fully server-rendered — no hydration cost, content is visible immediately
    · `preconnect` to both Google Fonts origins
    · `font-display: swap`
    · GA4 loaded `async`
    · Passive scroll listeners (`{ passive: true }`) on both scroll handlers
    · The sticky-CTA handler guards writes with a `last` flag to avoid layout
      thrash
    · `aspect-ratio` on all media containers prevents CLS from images
    · CSS-only carousels and accordions — no JS bundle for interactivity
  WEAKNESSES:
    · The stylesheet is UNMINIFIED (97KB with comments and indentation;
      realistically ~55–60KB minified, ~12KB gzipped) [EST]
    · NO lazy loading — `loading="lazy"` does not appear on any image
      [VERIFIED across all 60 raw HTML files]
    · Hero photography is delivered via CSS `background-image`, so it cannot be
      lazy-loaded, `srcset`-ed, `fetchpriority`-ed or served responsively —
      every viewport downloads the full-size asset
    · ~30 `.hero-e--photo-*` rules ship to every page even though each page uses
      one; the browser only fetches the matched one, but the CSS weight is
      carried site-wide
    · Mixed image formats (.png/.jpg/.webp/.svg) with no AVIF and no evident
      optimisation pipeline
    · The marquee duplicates the full logo set in markup (required for the
      -50% loop), doubling image element count on every page
    · Fonts are loaded via a plain `<link>` rather than `preload` — a
      render-blocking round trip after the CSS
    · No skeletons or placeholders — cards render empty-then-filled as images
      arrive (mitigated by `aspect-ratio` + the `--bg-warm` placeholder colour
      on every media container, which is a deliberate and effective choice)
    · `backdrop-filter` on the sticky header repaints on every scroll frame
      (minor, but measurable on low-end devices)

16. UNVERIFIABLE / NOT RETRIEVABLE
================================================================================

Nothing was blocked, gated or unreachable. The following are the only items in
this document that are NOT [VERIFIED], and the reason for each.

1. RENDERED APPEARANCE. No browser rendering or screenshot was available in
   this environment. Everything about how the design LOOKS in aggregate —
   actual visual density of the marquee, how the cream hero veil reads over
   each specific photo, whether text ever collides at intermediate widths,
   perceived hierarchy — is inferred from code, not observed.

2. SECTION HEIGHTS in §3 and §12 are [EST]. They are computed from padding +
   estimated content height at a 1440px viewport, not measured.

3. CONTRAST RATIOS in §14 are [EST]. They are arithmetically derived from the
   verified hex values using the standard WCAG relative-luminance formula, not
   measured against rendered pixels. Values involving alpha compositing (e.g.
   the .96-alpha header over arbitrary page content) are approximations.

4. THE ICON LIBRARY is [EST] as Feather/Lucide-family. The SVGs are inlined
   per-instance with no library attribution. The identification rests on the
   24×24 viewBox, 2px round-cap/round-join convention, and the fact that the
   checkmark data URI uses Feather's exact `polyline points='20 6 9 17 4 12'`.
   It could equally be a hand-drawn set following the same conventions.

5. MISSING JAVASCRIPT. app.js (74 lines) contains ONLY the header shadow, the
   mobile drawer, and the sticky CTA bar. It does NOT contain handlers for:
     · the FAQ accordion (`.faq-row.open`)
     · the pricing tab switcher (`.plan-option.is-active` /
       `.plan-detail.is-active`)
     · the carousel prev/next arrows (`.upgrade-nav`,
       `.review-carousel__arrow`)
     · the modal trigger (`[data-tanous-open-modal]`, which the GA4 script
       explicitly listens for)
   These behaviours are fully STYLED in the CSS, and the state classes are
   clearly designed for. The handlers must therefore live in inline scripts
   emitted per-section by Bricks Builder, which I did not isolate from the
   page HTML. I have NOT verified whether these interactions actually function
   on the live site. If you are replicating, budget for writing ~40 lines of JS
   to make the FAQ, tabs, carousels and modal work.

6. MARQUEE MARKUP DUPLICATION. The `translateX(-50%)` keyframe implies the logo
   set is duplicated in the DOM for a seamless loop. I confirmed 22 logo images
   with alt text plus 22 with empty alt on the homepage, which is consistent
   with duplication, but I did not verify the wrapper structure that makes the
   loop seamless.

7. GRAVITY FORMS' OWN STYLESHEET. Gravity Forms normally enqueues its own CSS.
   No such stylesheet link appears in the page <head>, which suggests GF's
   default CSS is disabled and the theme's `!important` overrides carry the
   entire form appearance. I could not confirm the plugin setting, so the exact
   cascade in a live browser is unverified.

8. ACTUAL IMAGE DIMENSIONS AND FILE SIZES were not fetched. The performance
   commentary about unoptimised delivery is based on format mix, the absence of
   `srcset`/`loading="lazy"`, and the use of CSS background-images — not on
   measured payload.

9. THE `--red-soft: #FBE8E6` TOKEN is verified as declared and verified as
   never referenced in design-system.css. It could conceivably be used by an
   inline Bricks style I did not enumerate exhaustively across all 60 pages.

10. TWO PARALLEL DARK/RED VALUES (#EE2E2B vs --red #E5302B; #0D1A30 vs
    --bg-deeper #0E1A3C) are verified as present in the CSS. Whether this is an
    intentional secondary accent or drift from a later design pass is not
    determinable from the code.

11. NO BRAND PAGE EXISTS to confirm the palette and typography as
    *officially* sanctioned. /brand, /brand-kit, /press, /media-kit and
    /style-guide all 404 or are absent from the sitemap, and no footer link
    points to one. The `:root` block is therefore the highest available
    authority — which is strong, but it is a developer artifact rather than a
    published brand standard.
